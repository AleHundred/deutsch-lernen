# Projekt Deutsch — v0.1 Design Document (Post-Pivot)

*Version: 2026-04-24*
*Supersedes slot-classification-era design*

---

## 0. Context

### What happened before this document

v0.1 originally shipped `slot-classification` as the sole drill kind, targeting TeKaMoLo adverbial slotting. After one drill session, the user identified that:

1. Classification of adverbial phrases was too easy in isolation for her current knowledge level.
2. Example sentences used in explanations exposed gaps in more foundational skills (V2 word order, reflexive verb morphology) that classification drilling could not address.
3. Her self-assessment: *"I need more A2.1 exercises."*

This is accurate. Her passive comprehension is A2.2+, but her production floor has A1/A2.1 gaps in specific high-frequency skills that never solidified into automatic production. Building sophisticated A2.2 drills on a shaky A1/A2.1 foundation was premature.

### What this document covers

v0.1 is pivoting to target A2.1 production fundamentals. Scope: **five production drill kinds** covering the skills where production breaks down under time pressure. The existing infrastructure (schema base, Dexie, SM-2, scheduler, routing, Home/Summary UI) is retained. The `slot-classification` drill kind is deprecated but kept in git history and the DrillKind union (marked explicitly as deprecated) — it may return in v0.2 once foundations are solid.

### What this document does NOT cover

- Flashcards / vocabulary drills (user will handle externally)
- Original slot-classification improvements
- v0.2+ drill kinds (Perfekt production, Nebensatz word order, adjective declension, Konjunktiv II)
- Journal, streak tracking, stats dashboards, PWA manifest, sync
- UI polish beyond functional requirements

## 1. The five drills

### 1.1 Case selection (recognition)

**Skill:** given a preposition or verb in a sentence, identify which grammatical case it triggers.

**Task:** button-tap classification (Nom / Akk / Dat).

**Why recognition, not production:** case selection IS a classification task at heart. "Does `mit` take Dat or Akk?" has one correct answer per preposition; the user's job is to recognize which bucket the preposition falls into. Production here would be artificial.

**Format:**

```
ITEM 3 OF 15

Ich spreche mit der Frau.
                 ^^^
           highlight on "mit"

[ Nom ]  [ Akk ]  [ Dat ]

"I'm talking with the woman."
```

**Data shape:**
```ts
interface CaseSelectionParams {
  frame: string;                    // "Ich spreche mit der Frau."
  gloss: string;                    // "I'm talking with the woman."
  highlightStart: number;           // index in frame of the trigger
  highlightEnd: number;
  trigger: string;                  // the word being tested: "mit"
  triggerType:                      // for feedback and analytics
    | "preposition"
    | "verb-transitive"             // sehen, kaufen, lesen, etc. → Akk
    | "verb-dative"                 // helfen, danken, gratulieren → Dat
    | "sein-construction";          // "ist ___" → Nom
  correctCase: "nom" | "akk" | "dat";
  explanation: string;              // "mit always triggers Dativ"
}
```

**Seed size:** ~50 items. Breakdown:
- 20 Akk-only prepositions in context (für, ohne, durch, gegen, um) — 4 items each
- 20 Dat-only prepositions in context (mit, bei, von, zu, nach, aus, seit) — ~3 items each
- 10 verb-driven items (5 transitive verbs with Akk, 5 dative verbs with Dat)

**Wechselpräpositionen excluded from this drill.** They're genuinely two cases depending on context and belong in a separate item type or in case-morphology drill. In v0.1 case-selection, only unambiguous cases.

**Rule granularity:** per-trigger. Rules like `"mit-Dat"`, `"für-Akk"`, `"helfen-Dat"`, `"sehen-Akk"`. That's ~25 distinct rules.

**SRS grade mapping:**
- Correct, <2s → grade 5
- Correct, 2-4s → grade 4
- Correct, >4s → grade 3 + declarative flag
- Wrong → grade 1

### 1.2 Case morphology (production)

**Skill:** given a sentence frame with a blank where an article belongs, and with the case explicitly marked, produce the correct article form.

**Task:** type the correct article into a text input.

**Why production, not recognition:** this is exactly the firing-under-time-pressure skill the drill targets. Recognition (picking from buttons) would let the user identify `der` vs `den` by visual comparison — a different cognitive task than retrieving it from gender+case.

**Format:**

```
ITEM 7 OF 15

Ich fahre mit [Dat] ___ U-Bahn.
"I go by U-Bahn."

[text input: ____________]
                [Submit]
                or Enter
```

**Key design move — explicit case markers in prompt:** `[Dat]` is shown next to the preposition. This removes ambiguity about which step the user is being tested on. The user is being tested on morphology (gender + case → article form), not on case selection (which is drill 1.1). Splitting the two eliminates diagnostic confusion: if the user types `die`, we know exactly what the error is (wrong feminine-Dat form), not "wrong case or wrong gender or both."

**Data shape:**
```ts
interface CaseMorphologyParams {
  frame: string;                    // "Ich fahre mit ___ U-Bahn."
  caseMarker: "Nom" | "Akk" | "Dat"; // shown in UI next to trigger position
  caseMarkerPosition: number;       // index in frame where marker renders
  gloss: string;                    // "I go by U-Bahn."
  expected: string;                 // "der"
  alternatives?: string[];          // rare, e.g. indefinite also valid
  gender: "m" | "f" | "n" | "pl";
  case: "nom" | "akk" | "dat";
  definiteness: "def" | "indef";
  trigger: string;                  // for cross-drill analytics
}
```

**Seed size:** ~60 items. Breakdown:
- 3 cases × 4 genders × 2 definiteness = 24 grid cells
- 2-3 items per cell
- Wechselpräp pairs (same preposition, different case based on direction vs location): 10 pairs = 20 items

**Rule granularity:** per-combination. Rules like `"akk-m-def"`, `"dat-f-indef"`, `"dat-m-def-wechsel-auf"`. ~30 distinct rules including Wechsel subdivisions.

### 1.3 Verb conjugation (production)

**Skill:** given an infinitive and a subject pronoun, produce the correct present-tense conjugated form.

**Task:** type the conjugated verb.

**Scope:** present tense only, irregular verbs only. Regular verbs (`spielen → du spielst`) are not the user's weak point; drilling them wastes cycles.

**Format:**

```
ITEM 4 OF 15       e→i    e→ie    a→ä    irreg    modal

sprechen → du ___
"to speak"

[text input: ____________]
                [Submit]
```

**Data shape:**
```ts
interface VerbConjugationParams {
  infinitive: string;               // "sprechen"
  infinitiveGloss: string;          // "to speak"
  person: "ich" | "du" | "er" | "wir" | "ihr" | "sie";
  expected: string;                 // "sprichst"
  alternatives?: string[];
  irregularityType:
    | "e-to-i"
    | "e-to-ie"
    | "a-to-ae"
    | "full-irregular"
    | "modal"
    | "regular-contrast";           // trap items: NO stem change (wir/ihr/sie forms)
  regularExpected: string;          // what naive regular conjugation would produce
}
```

**Irregularity categories and seed allocation:**
- **e→i** (sprechen, geben, nehmen, helfen, essen, treffen, vergessen): 7 verbs × ~3 forms (du, er, + one regular-contrast plural) = 21 items
- **e→ie** (lesen, sehen, empfehlen): 3 verbs × 3 forms = 9 items
- **a→ä** (fahren, schlafen, tragen, waschen, fallen, halten, lassen, laufen): 8 verbs × 3 forms = 24 items
- **full-irregular** (sein, haben, werden, wissen, tun, mögen): 6 verbs × 6 persons = 36 items
- **modals** (können, müssen, wollen, sollen, dürfen, mögen): 6 modals × 3 irregular persons + 1 plural contrast each = 24 items

Total: ~114 items.

**Rule granularity:** per-verb-form. Rules like `"sprechen-du"`, `"sein-ich"`, `"fahren-er"`. ~110 distinct rules. Per-category aggregates computed at summary level.

### 1.4 Reflexive production (production)

**Skill:** given a subject pronoun and a reflexive infinitive construction, produce a full conjugated sentence with correct reflexive pronoun and verb placement.

**Task:** type the full sentence.

**Why this is the hardest Group B drill to design first:** it integrates three skills simultaneously — verb conjugation, pronoun selection, and V2 word order. Getting it right tests whether all three skills are automatic; getting it wrong diagnoses which is broken.

**Format:**

```
ITEM 9 OF 15

ich + sich treffen + mit Lex
"I meet with Lex."

[text input: _________________________________]
                        [Submit]
```

**Expected:** `Ich treffe mich mit Lex.`

**Data shape:**
```ts
interface ReflexiveProductionParams {
  subject: "ich" | "du" | "er" | "wir" | "ihr" | "sie";
  reflexiveInfinitive: string;      // "sich treffen"
  objectPhrase?: string;            // "mit Lex" — optional, some reflexives are intransitive
  gloss: string;                    // "I meet with Lex."
  expected: string[];               // all valid orderings, e.g. ["Ich treffe mich mit Lex."]
  reflexiveCase: "akk" | "dat";     // most are Akk; dat when there's a direct object
  verbIrregularity?: string;        // if verb is irregular, reuses verb-conjugation's type
  commonErrors: Array<{             // pre-computed error patterns for feedback
    pattern: string;
    diagnosis: string;
  }>;
}
```

**Seed size:** ~40 items. Breakdown:
- 10 high-frequency reflexive verbs (sich treffen, sich freuen, sich interessieren, sich ärgern, sich entschuldigen, sich anziehen, sich waschen, sich fühlen, sich setzen, sich unterhalten)
- ~4 items per verb, varying subject person

**Rule granularity:** per-verb-person combination. Rules like `"sich-treffen-ich"`, `"sich-freuen-du"`. ~40 rules.

**Evaluator complexity:** this drill has the most complex evaluator. Must check:
1. Verb is correctly conjugated for the subject (reuses conjugation logic)
2. Reflexive pronoun matches subject and case (mich/dich/sich/uns/euch/sich)
3. Verb is in position 2 (V2 word order)
4. Reflexive pronoun is in the correct position (typically right after the verb in main clauses)

Each of these can fail independently. Error diagnosis surfaces which specific step broke.

### 1.5 V2 word order (production)

**Skill:** given scrambled sentence components, produce a main clause with the conjugated verb in position 2.

**Task:** type the correctly-ordered sentence.

**Why this is last (hardest):** multiple valid orderings per item (position 1 can be subject, adverbial, or object), evaluator must accept any grammatically correct ordering.

**Format:**

```
ITEM 12 OF 15

Components: ich | treffe | heute Nachmittag | mit Lex | mich | im Görli
"I'm meeting Lex in Görli this afternoon."

[text input: _________________________________]
```

**Valid answers (accept any):**
- `Ich treffe mich heute Nachmittag mit Lex im Görli.`
- `Heute Nachmittag treffe ich mich mit Lex im Görli.`
- `Mit Lex treffe ich mich heute Nachmittag im Görli.`
- `Im Görli treffe ich mich heute Nachmittag mit Lex.`

All valid. All have `treffe` in position 2. All use all components.

**Data shape:**
```ts
interface V2WordOrderParams {
  components: string[];             // unordered chunks
  gloss: string;                    // English meaning
  conjugatedVerb: string;           // "treffe" — must be in position 2
  subject: string;                  // "ich" — for tracking positions
  reflexivePronoun?: string;        // "mich" if reflexive
  validOrderings: string[];         // pre-computed list of accepted answers
  minComponentsCount: number;       // must use at least this many (usually all)
}
```

**Seed size:** ~30 items. Focus on patterns:
- 10 items with subject + verb + object + adverbial (basic structure)
- 10 items with reflexive verbs (integrates with drill 1.4)
- 10 items with multiple adverbials (foreshadows TeKaMoLo in v0.2)

**Rule granularity:** per-base-sentence. One rule per scrambled item because the "pattern" being tested (V2 structure) is the same across all items. ~30 rules.

**Evaluator:** pure structural check. Parse user input as tokens, verify:
1. Conjugated verb is the second "syntactic slot" (word 2 if position 1 is one word; otherwise words 2 onward after a multi-word position-1 phrase)
2. All required components are present
3. No extraneous words added

Not string-match against `validOrderings`. Structural validation. This is the hardest evaluator to write correctly.

## 2. Shared infrastructure

### 2.1 Generator interface (shared across all five drills)

```ts
interface ProductionPrompt {
  displayPrompt: ReactNode;         // rendered prompt (frame with blank, infinitive+person, scrambled chunks)
  gloss: string;                    // English meaning
  inputType: "single-word" | "sentence" | "classification";
  expectedAnswers: string[];        // all valid answers
  grammaticallyContrastive: string[]; // forms that are NEVER typos (for Levenshtein exclusion)
  rule: string;                     // SRS aggregation key
  buildFeedback: (userAnswer: string, correct: boolean) => FeedbackContent;
}

interface FeedbackContent {
  correctAnswer: string;
  userAnswer: string;
  explanation: string;              // primary teaching text
  paradigm?: ReactNode;             // optional full paradigm (for conjugation)
  compareItems?: Array<{ form: string; label: string }>;
  specificErrorType?: string;       // "regular-overgeneralization", "wrong-reflexive-pronoun", etc.
  capitalizationWarning?: string;   // if soft-warning applies
}
```

All five drill generators produce this shape. The DrillSession UI component is generator-agnostic.

### 2.2 Shared evaluator

```ts
function evaluateProduction(
  userAnswer: string,
  prompt: ProductionPrompt,
  options: {
    levenshteinTolerance?: number;  // default 1
    capitalizationMode: "strict" | "warn" | "ignore";
  }
): EvaluationResult {
  const normalized = userAnswer.trim();

  // Exact match
  if (prompt.expectedAnswers.includes(normalized)) {
    return { correct: true, grade: 5, feedback: prompt.buildFeedback(normalized, true) };
  }

  // Capitalization warning path (for "warn" mode)
  if (options.capitalizationMode === "warn") {
    const ciMatch = prompt.expectedAnswers.find(a => a.toLowerCase() === normalized.toLowerCase());
    if (ciMatch) {
      const warning = buildCapitalizationWarning(normalized, ciMatch);
      return {
        correct: true,
        grade: 4,
        feedback: { ...prompt.buildFeedback(normalized, true), capitalizationWarning: warning }
      };
    }
  }

  // Levenshtein-1 typo check, excluding grammatically-contrastive forms
  if (options.levenshteinTolerance ?? 1 > 0) {
    const typoMatch = findTypoMatch(
      normalized,
      prompt.expectedAnswers,
      prompt.grammaticallyContrastive,
      options.levenshteinTolerance ?? 1
    );
    if (typoMatch) {
      return {
        correct: true,
        typo: true,
        grade: 4,
        feedback: prompt.buildFeedback(normalized, true),
        diff: highlightDiff(normalized, typoMatch.match),
      };
    }
  }

  return { correct: false, grade: 1, feedback: prompt.buildFeedback(normalized, false) };
}

// Key helper — drill-kind-specific grammatically-contrastive lists
const CONTRASTIVE_SETS = {
  articles: ["der", "die", "das", "den", "dem", "ein", "eine", "einen", "einem", "einer"],
  reflexives: ["mich", "dich", "sich", "uns", "euch"],
  // per-verb paradigms computed at seed time for conjugation
};
```

Drill-specific `grammaticallyContrastive` is populated by each generator. The evaluator is otherwise completely drill-agnostic.

**Case selection (drill 1.1) uses a simplified path:** it's a button tap, so the evaluator just compares the tapped value to `correctCase`. No Levenshtein, no capitalization. This drill could use a separate evaluator or a thin wrapper — TBD in implementation.

### 2.3 Shared UI components

**`<ProductionDrill>`** — renders `displayPrompt`, text input, submit button. Handles Enter-to-submit. On submit, calls evaluator, displays `FeedbackContent` below. Used by drills 1.2, 1.3, 1.4, 1.5.

**`<ClassificationDrill>`** — renders prompt with button row. Used by drill 1.1 (case selection). Similar to existing slot-classification UI but with 3 buttons instead of 4.

**`<FeedbackPanel>`** — renders `FeedbackContent`. Shared by both drill types.

### 2.6 SRS grade mapping (consolidated across drills)

Production drills (1.2, 1.3, 1.4, 1.5):
- Exact correct, <3s typing → grade 5
- Exact correct, 3-6s → grade 4
- Capitalization warning (soft) → grade 4
- Levenshtein-1 typo → grade 4
- Correct, >6s → grade 3 + declarative flag
- Wrong → grade 1

Recognition drill (1.1):
- Correct, <2s → grade 5
- Correct, 2-4s → grade 4
- Correct, >4s → grade 3 + declarative flag
- Wrong → grade 1

Thresholds tunable after first real drilling data.

## 3. Build sequence

Order is by increasing complexity. Each checkpoint is ~1-2 hours of Claude Code work plus your review.

### Phase A — Infrastructure pivot (2-3 sessions)

**Checkpoint A1:** Remove slot-classification from active use, mark deprecated. Schema pivot to discriminated union. Dexie migration (wipe + reseed on load, kept for now). Update scheduler to work with typed items.

**Checkpoint A2:** Build shared `ProductionPrompt` / `FeedbackContent` types. Write shared evaluator with Levenshtein-1 typo logic and capitalization warn mode. Write `findTypoMatch` and `buildCapitalizationWarning` helpers. Full test coverage for evaluator.

**Checkpoint A3:** Build `<ProductionDrill>` and `<ClassificationDrill>` shared UI components. Build `<FeedbackPanel>`. No drill-specific logic in UI yet.

### Phase B — Drill 1.1: Case selection (2 sessions)

**Checkpoint B1:** Generator + seed data (~50 items). Rule: per-trigger. You curate seed after CC generates first pass.

**Checkpoint B2:** Integrate with scheduler, wire to ClassificationDrill UI, session summary adds per-trigger accuracy breakdown. Ship as v0.2.0 (first usable build after pivot).

### Phase C — Drill 1.2: Case morphology (2 sessions)

**Checkpoint C1:** Generator + seed data (~60 items including Wechsel pairs). Case markers in prompt.

**Checkpoint C2:** Integration + summary. Ship as v0.2.1.

### Phase D — Drill 1.3: Verb conjugation (3 sessions)

**Checkpoint D1:** Seed data (~114 items across 5 categories). You curate — this is the largest seed.

**Checkpoint D2:** Generator + regular-overgeneralization error detection. Evaluator extension for per-verb paradigm awareness.

**Checkpoint D3:** Integration + summary. Per-category analytics. Ship as v0.2.2.

### Phase E — Drill 1.4: Reflexive production (3 sessions)

**Checkpoint E1:** Seed data (~40 items) and generator.

**Checkpoint E2:** Structured evaluator — checks verb conjugation, reflexive pronoun match, V2 position, reflexive pronoun position. This is the most complex evaluator.

**Checkpoint E3:** Integration + summary. Ship as v0.2.3.

### Phase F — Drill 1.5: V2 word order (3 sessions)

**Checkpoint F1:** Seed data (~30 items) and generator. Pre-compute `validOrderings` array per item.

**Checkpoint F2:** Structural evaluator — tokenize user input, identify verb position, verify all components present. Most complex evaluator of the five. Test coverage is critical.

**Checkpoint F3:** Integration + summary. Ship as v0.2.4 — v0.1 COMPLETE.

### Timeline

Realistic estimate: 5-7 weekends of focused CC work + seed curation. Users should expect ~8 weeks from start to v0.1 complete if protecting weekends.

Phases ship incrementally. After Phase B completes, you have a usable case-selection drill. After Phase C, you have both case drills. You do NOT need to wait for Phase F to start drilling. This is the explicit value of the incremental build: every phase ship is a genuine improvement to your daily practice.

## 4. Scope discipline

### Hard lines

- No flashcards. Vocabulary work happens elsewhere.
- No journal, no streak tracking, no PWA manifest.
- No drill kinds beyond the five specified. If a sixth kind seems needed mid-build, it becomes v0.3 — do not silently expand v0.1.
- No UI polish beyond functional requirements. Dark theme, readable, keyboard-navigable. Not beautiful.
- No settings panel, no user preferences, no themes.
- Slot-classification remains deprecated — do not re-enable, extend, or "fix."

### What we'll reconsider post-v0.1

- Adjective declension drill (big, worth its own kind in v0.2)
- Perfekt production drill (was original v0.1 plan, may return for v0.2)
- Nebensatz word order (depends on how V2 drill lands)
- Session history view beyond latest summary
- Export/import for SRS backup
- Paper-drilling or external practice integration

### Explicit non-goals

This app will never be:
- A complete German learning platform
- A replacement for textbooks, courses, or tutors
- Duolingo-style gamification
- A consumer product for other learners

It is a personal tool built for one user, addressing specific production gaps, with scope narrowly fitted to those gaps.

## 5. Open decisions for implementation

### 5.1 Case selection — do we show hover labels for Nom/Akk/Dat buttons?

The slot-classification drill has hover labels on Te/Ka/Mo/Lo buttons. Should case-selection replicate this pattern?

**Argument for:** consistency with existing drill. New users (future you six months from now) might appreciate reminders of what each case is.

**Argument against:** you already know what Nom/Akk/Dat mean. The slot-classification labels were genuinely needed because Te/Ka/Mo/Lo are less common labels. Nom/Akk/Dat are basic.

**Recommendation:** skip labels for v0.1. Add later if needed.

### 5.2 V2 evaluator — structural or string-match?

Structural evaluation (parsing user input, verifying verb position) is harder to write but catches more valid answers. String-match against pre-computed `validOrderings` is simpler but might reject valid orderings not pre-computed.

**Recommendation:** start with string-match for v0.1 (generate all valid orderings at seed time). Move to structural validation in v0.2 if string-match shows meaningful false-negative rate.

### 5.3 Seed curation — how interactive?

For ~300 seed items across five drills, you'll want to review most of them for vocabulary fit. Options:

**Option 1:** Claude Code generates seed files, you review in the repo. Fast iteration but lower engagement with the content.

**Option 2:** Seed generation happens in this chat, you mark items to cut/modify before they go to CC. Slower but higher engagement and better content-fit.

**Recommendation:** Option 2 for case-selection and case-morphology (~110 items combined) since vocabulary fit matters. Option 1 for verb-conjugation (~114 items) since the content is mostly verb paradigms, not vocabulary. Mix for the rest.

## 6. Success criteria for v0.1

After v0.1 ships and you drill consistently for ~2 weeks, we evaluate:

1. **Response times** on the top 20 rules per drill kind. Are they dropping? If yes, procedural automaticity is forming. If no, the drill isn't working.

2. **Error patterns in summaries.** Are specific rules persistently weak? That's useful diagnostic data regardless of whether times drop.

3. **Your subjective experience.** Does drilling feel like learning German, or does it feel isolated like v0.1's slot-classification did? If the latter, we have deeper questions to answer.

4. **Transfer to non-app production.** Can you write a German paragraph without the app helping? Can you have a 2-minute German conversation? The drill is a means, not an end. If the app's numbers improve but your production in the wild doesn't, something is wrong.

Criterion 4 is the real test. The app produces data; your life produces evidence.

## 7. Pivot history

For Claude Code's context, the sequence:

- **Original v0.1:** single drill kind `word-order-perfekt`. Not built.
- **Pivoted v0.1 (first):** single drill kind `slot-classification` (TeKaMoLo). Built and shipped.
